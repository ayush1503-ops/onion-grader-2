# Chapter 24 — Testing & Evaluation Metrics
> ➕ **ADDITIONAL PROJECT KNOWLEDGE**.

## 1. Learning Objectives
1. Evaluate on truly unseen images. 2. Know accuracy, precision, recall, F1. 3. Read a confusion matrix. 4. Evaluate a rule-based system honestly.

## 2. Simple Explanation
"Does it work?" is not a feeling — it's a number computed on images the system **never saw during development**. A **confusion matrix** counts how often each true class was predicted as each class; from it come precision, recall and F1.

## 3. Technical Explanation
```text
                 predicted
             GOOD  BAD   ROTTEN
true GOOD     40    3      1
true BAD       4   30      2
true ROTTEN    0    2     35
```
- **Accuracy** = correct / total (misleading if classes are imbalanced).
- **Precision** (per class) = of all "rotten" calls, how many were truly rotten. High precision = few false alarms.
- **Recall** (per class) = of all true rotten, how many you caught. High recall = few missed.
- **F1** = harmonic mean of precision & recall (balances both).
```python
from sklearn.metrics import classification_report, confusion_matrix
print(confusion_matrix(y_true, y_pred))
print(classification_report(y_true, y_pred))
```

## 4. Real-World Example
Medical screening: you'd rather have high recall (catch all diseases) even if precision drops (some false alarms).

## 5. OpenCV Example — evaluating a rule-based system

# Chapter 26 — Honest Limitations: What a Camera Can & Can't See
> ➕ **ADDITIONAL PROJECT KNOWLEDGE** — read this before you present the project to anyone.

## 1. Learning Objectives
1. State exactly what visible-image analysis can and cannot detect. 2. Keep your project's claims scientifically reasonable.

## 2. Simple Explanation
Your analyzer sees a **flat photo of the surface**. It can measure what's *visible*: color, spots, texture, shape. It cannot see *inside* the onion. Claiming otherwise would be like a doctor diagnosing internal organs from a passport photo.

## 3. Technical Explanation — what a normal RGB camera **can** potentially detect
- ✅ Visible **discoloration** (brown, dark, green patches) — via HSV features.
- ✅ Visible **surface damage** (bruises, cuts, dried skin breaks).
- ✅ Visible **spots & mold** on the outside.
- ✅ **Shape** abnormalities (deformed, sprouting, shrunken) — via contour features.
- ✅ **Texture** changes (wrinkled, shriveled skin) — via gray-level standard deviation.

## What it **cannot** reliably detect (and you must say so)
- ❌ Hidden **internal rot** — a healthy-looking outside can hide a rotten core.
- ❌ Internal damage, internal moisture, hollow centers.
- ❌ Defects on the side facing away from the camera.
- ❌ Taste, smell, firmness, chemical composition.
- ❌ Anything invisible in the image, period.

## 4. Real-World Example
Real produce grading uses additional sensors — weight, firmness (touch), near-infrared spectroscopy, X-ray — precisely because RGB cameras can't see inside.

## 5. OpenCV Example — the honest framing in your code/output
```python
print("NOTE: this analysis is based on visible surface features only.")
print("It cannot detect internal defects (e.g., hidden rot).")
```

## 6. 🧅 Onion Project Example — the honest README statement
> "This tool grades onion **appearance** from a single visible-light photo. It detects visible blemishes, discoloration and shape defects. It does **not** detect internal rot or hidden damage; onions that look clean can still be internally spoiled."
